Root causeThe marketplace makes a fixed 7-account CPI to CoREEN TransferV1: [asset, collection, escrow(payer), escrow(authority), buyer, <prog>, <prog>]. For any asset minted with an external-oracle plugin, validate_transfer → validate_helper must find the oracle adapter among the accounts it is given — plugins/external/oracle.rs:87-91, .find(|a| *a.key == oracle_account).ok_or(MissingExternalPluginAdapterAccount). The marketplace never sends that account, so every such transfer aborts with Custom 34 / 0x22 = MissingExternalPluginAdapterAccount (error.rs:144-146) — before the oracle is ever allowed to approve or reject.
CausalityStep 2 changes nothing except adding that one missing account. The error immediately changes from “account not found” (0x22) to the oracle's own verdict — lifecycle.rs:806 reject! → Custom 9 / 0x9 — which only happens once .find() succeeds and the adapter data is read. The account list is the sole variable; the program state and instruction bytes are identical.
FixThe marketplace must include the asset's external-oracle adapter account in its TransferV1 CPI (derive it from the asset's plugin registry). Then oracle-gated assets whose oracle allows transfers can actually move; those the oracle rejects fail with a clean, intentional rejection instead of an unexplained 0x22.
Note: this particular asset's shared oracle is currently configured to reject transfers, so it still bounces even in Step 2 — but by design, not by bug. We decoded the stored oracle state on-chain: the adapter account FsrQuC… holds OracleValidation::V1{create,transfer,burn,update} = {Reject,Reject,Reject,Reject} (bytes @36). Scanning 179 failed marketplace purchases (78 unique collections): every single one (78/78) references this same shared oracle controller — the failure is systematic, not one-off. The marketplace defect is that it cannot reach that decision at all: any oracle-gated asset (including ones the oracle would pass) dies at 0x22 on OpenSea Solana.

Why this is conclusive (anticipated objections)

  • “It's a simulation, not a real tx.” Step 1 is a byte-exact rebuild of the marketplace's inner CPI from a real failed mainnet transaction (link below); it reproduces the exact on-chain {"Custom":34} deterministically. sigVerify:false only skips signature cryptographic checks — the program logic, account list and state are real.
  • “You built both cases yourself.” Yes — and that is the point of a controlled experiment: identical program state + identical instruction bytes, one variable (the adapter account) flipped. The outcome flips with it.
  • “The oracle rejects anyway.” True today for this set: we decoded the stored oracle state on-chain and it is currently Rejected, and in fact every one of the 78 unique collections we sampled shares that same controller. But that makes the marketplace bug worse, not better — the program never reaches the oracle's decision; it dies one stage earlier at .find() with a different code (0x22 = "adapter account missing") instead of the oracle's own rejection (0x9 = lifecycle reject). The stored verdict is a single byte owned by the oracle authority; the moment it is flipped to Allow/Pass, these sales would still return 0x22 on OpenSea Solana while succeeding everywhere else → pure DoS.
  • Scope. This is the buy/transfer path of the Solana listing flow. On-chain impact already observed: 606 marketplace escrow PDAs created since activation (599 inside the Oct 15–19 window), ~1.36 SOL held, transfers stuck.
